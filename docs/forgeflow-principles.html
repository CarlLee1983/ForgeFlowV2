PHASE 01 • SPECIFICATION REVOLUTION

從口頭提示，
轉向確定性軟體契約

向團隊解說：為什麼傳統的「Prompt 道德勸說」永遠會失效，而 ForgeFlow 如何將規格化為實體卡榫。

「用不可篡改的軟體合約限制代理人權限，用作業系統確定性的測試命令取代 AI 的主觀自信。」

FAIL PATTERN • PROMPT-DRIVEN

依賴道德勸說的脆弱假設

在 Markdown 寫滿原則（如「請一定要測邊界條件、請勿亂裝套件」）。這類非約束性指導隨上下文增長而迅速衰減，最終使團隊陷入盲信與反覆猜疑。

SUCCESS PATTERN • SPEC-DRIVEN

由機械工具執行的物理卡榫

意圖沉澱為結構化的任務卡與測試指標。代理人的每一項宣稱都必須經過作業系統 Exit Code 與集合差集運算的硬性查驗，未達標準即刻中斷。

PHASE 02 • MECHANICAL TRIAD

防幻覺的實質運作：三重機械檢驗

不靠另一顆 AI 來評測，而是用純 POSIX Shell、正則表達式與 CPU 二進制測試構築三重防線。

GATE 01

集合雙向追溯 (Traceability)

規格書內列出的每一個 AC，必須在測試代碼中存在完全精確的標記。以 UNIX diff 進行差集比對，少一個立即報錯退出。

GATE 02

作業系統退出碼 (Exit Status)

語言模型對話中的承諾毫無效力。系統僅承認 make verify 執行後由作業系統內核回傳的 $? = 0 狀態碼。

GATE 03

權限邊界約束 (Authority Set)

嚴格限制代理人僅能執行已授權的操作。若在未開放 add_dependency 的情況下修改套件表，結案檢查立即判定失敗。

底層技術：POSIX Shell (set -eu) 字串解析：Stream Editor (sed) 集合運算：UNIX diff -u 零依賴：Zero External Runtime

追溯性閘門的底層技術實作原理

檢查器不依賴 Python、Node 或外部套件，而是直接使用相容 POSIX 的 /bin/sh 原生工具。透過 sed 提取規格與程式碼的 AST Token 集合，並以 UNIX 核心工具 diff -u 進行差集計算。任何單向不匹配，核心進程直接拋出 Exit Code 1，硬性阻斷 CI 流水線。

scripts/check-traceability.sh
POSIX SHELL VERIFICATION GATE 
# 1. 提取 specs/stories/.../acceptance.md 中的所有 AC 編號
sed -n 's/^[[:space:]]*\* \[ \] \(AC-[0-9][0-9]*\):.*/\1/p' acceptance.md | sort > acceptance-ids

# 2. 提取測試代碼中的測試案例標記
sed -n 's/^[[:space:]]*test("\(AC-[0-9][0-9]*\):.*/\1/p' order.test.ts | sort > test-ids

# 3. 進行嚴格集合比對：只要差異存在，命令直接拋出 Exit 1 崩潰中斷！
if ! diff -u acceptance-ids test-ids; then
    printf 'acceptance and executable test identifier sets differ\n' >&2
    exit 1
fi
PHASE 03 • MAPPING GRANULARITY

映射粒度：測試案例而非個別檔案

答覆團隊疑問：一個 Story 有 10 個 AC 檢查點，不需要開 10 個 test.ts，而是同一個檔案裡的 10 個測試區塊。

底層技術：Node.js Test Runner / Vitest / Go Test 斷言機制：Strict Assertions 標記機制：Regex String Anchoring

單元測試與 AC 的語義錨定技術

現代測試框架原生支援字串標籤過濾。ForgeFlow 利用測試描述字串作為 AST 錨定點（test("AC-01: ...")），在編譯期與執行期均保持單一檔案的內聚性，同時提供粒度達到單一斷言（Assertion）層級的檢驗報告。

test/order-total.test.ts
NODE.JS TEST RUNNER • 1-TO-1 SEMANTIC ANCHOR 
import test from "node:test";
import assert from "node:assert/strict";

// 對應 AC-01: 金額計算加總
test("AC-01: sums line item prices in cents", () => {
  assert.equal(calculateOrderTotal([{ price: 1250, qty: 2 }]), 2500);
});

// 對應 AC-02: 空購物車回傳零值
test("AC-02: returns zero for an empty order", () => {
  assert.equal(calculateOrderTotal([]), 0);
});

// 對應 AC-03: 負數單價拋出特定業務錯誤
test("AC-03: rejects invalid unit prices", () => {
  assert.throws(() => calculateOrderTotal([{ price: -1, qty: 1 }]));
});

任務卡解析器的底層技術原理

scripts/story-check 與 scripts/verification-check 內部實作了一套純 Shell 狀態機，逐行分析 Markdown Token。它將任務卡視為強型別結構體（Struct），驗證項目包含：權限遮罩（Authority Mask）、安全邊界欄位（Trust Boundary）、與預期例外集合（Expected Errors）。任何欄位缺失或格式不合法均在預檢期（Preflight）直接攔截。

PHASE 05 • CONTRACT DSL ARCHITECTURE

任務卡的底層語法：Contract DSL 深度解析

向團隊交代真相：任務卡外觀是 GFM Markdown，底層則是透過 POSIX 詞法分析器與有限狀態機（FSM）逐行審計的 5 大強型別語法結構。

語法架構：GFM-Compliant Contract DSL 詞法解析器：scripts/story-check Lexer 驗證原則：Zero Ambiguity / Zero Placeholder

為什麼「看似 Markdown」卻能做到編譯器等級的語法查核？

一般人把 Markdown 當隨筆筆記；ForgeFlow 則將其視為一門**受限的領域特定語言（DSL）**。人類閱讀時好讀美觀，但 Shell 腳本在底層會啟動狀態機，將每一個符號拆解為 Token 並嚴格核對欄位數與字面量，杜絕 AI 產生任何模糊發揮的空間。

1. 識別碼正規文法 (Story ID Grammar) Regex Scanner

任務卡目錄與 ID 絕非自由命名，必須符合 BNF 形式文法，嚴禁小寫開頭或底線符號。

^[A-Z][A-Z0-9]*(-[A-Z0-9]+)*-[0-9]+(-[a-z0-9-]+)?$
合規：DBC-001, FF-PLAT-009 | 違規：story-01 (拋出 ERROR Invalid ID)
2. 宣告式鍵值對 (Declaration Bullet) Section FSM

所有系統參數使用單行嚴格宣告，底層函式 forgeflow_read_declaration() 逐行讀取冒號後的值。

* <Key>: <Value> (例：* Security sensitive: yes)
限制：值限定為布林或特定列舉，嚴禁跨行縮排或未定義關鍵字
3. 驗收核取方塊 (Checkbox AC Notation) forgeflow_is_placeholder

驗收條款必須使用標準方塊符號，底層函式會主動掃描角括號，全面禁止任何占位符。

* [ ] AC-<Number>: <Criterion Prose>
抓包：若包含 <TODO>, TBD, N/A 直接判定 NOT READY 退件
4. 固定五欄表格 (Strict 5-Column Table) forgeflow_is_five_column_separator

證據對照表欄位完全固定。底層逐行計算管線符號 |，多一欄或少一欄均直接語法錯誤。

| AC | Method | Evidence | Fixture | Expected observation |
限制：Method 只能是 test|command|human；Evidence 必須是反引號字面量
5. 結案斷言語法 (Evidence Observation Syntax) verification-check --result

在結案檔案 verification.md 中，AI 不得使用自由對話報告，必須輸出包含全形破折號的斷言語法：

* `AC-xx`: pass — `<精確測試案例標籤或指令>`
狀態關鍵字僅限 pass, fail, blocked, skipped。若任何 AC 缺漏或未對齊，系統即刻判定為 VERIFICATION_PARTIAL (拒絕合併)。
PHASE 06 • THE CLOSED-LOOP PIPELINE

SDD + TDD 雙重閉環：工程流水線全景

向團隊做最後總結：ForgeFlow 不是外掛插件，而是讓「規格驅動（SDD）」與「測試驅動（TDD）」在機器層面完美咬合的閉環管線。

STAGE 01

SDD 意圖固化

人類或架構師定義 story.md 與 acceptance.md。邊界、輸入輸出、預期錯誤與權限邊界在此刻鎖死。

產出：規格考卷
STAGE 02

TDD 測試先行

AI 代理人接單，不得直接寫功能。必須先在測試檔中撰寫帶有 AC-xx 標籤的紅燈測試（Failing Tests）。

實作：Red-to-Green
STAGE 03

物理機械對帳

執行 scripts/check-traceability.sh 與 make verify。UNIX diff 差集核對題號，CPU 執行真實二進制斷言。

查核：Exit Code 0
STAGE 04

結案證據遞交

生成 verification.md，將每個 AC 綁定通過的測試日誌。唯有完全無缺漏，才放行進入人類審查（Human Review）。

交付：確定性成果

「規格（SDD）給出邊界與題目，測試（TDD）提供客觀答案，機械檢查器則是不收賄賂的閱卷官。」
